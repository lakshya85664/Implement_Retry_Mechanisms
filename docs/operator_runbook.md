# Operator Runbook — Shipping Label Retry Workflow

## 1. Purpose

This runbook explains how to operate, inspect, and recover the shipping-label workflow when provider calls succeed, fail, time out, or are delivered more than once.

The implementation uses a simulated shipping provider. No production shipping API is contacted.

## 4. Operator actions by state

| Workflow state | Meaning | Required operator action |
|---|---|---|
| created | Workflow input accepted | Validate shipment details and authorization |
| running | An attempt is executing | Monitor the attempt; avoid duplicate submissions |
| retrying | A transient failure occurred | Allow the configured bounded retry policy to continue |
| completed | Label creation succeeded | Verify label ID and continue fulfilment |
| needs_review | Permanent failure or retry exhaustion | Stop automatic processing and investigate |
| cancelled | Workflow was cancelled | Confirm cancellation and check for unintended provider side effects |

## 5. Failure handling procedures

### A. Successful label creation

1. Check that the workflow status is `completed`.
2. Record the returned label ID.
3. Confirm the shipment and label association.
4. Continue downstream fulfilment.

No recovery action is required.

### B. Transient failure and retry exhaustion

1. Inspect the attempt log and error type.
2. Confirm the configured maximum attempt count.
3. Check provider availability and error history.
4. Stop automatic retries after the configured limit.
5. Investigate the shipment before authorizing another operation.

Do not repeatedly submit new requests with different idempotency keys.

### C. Timeout

A timeout only means that the caller stopped waiting. It does not prove that the provider did not complete the operation.

1. Retrieve the original idempotency key.
2. Query the provider for that key.
3. If a label exists, reconcile the workflow with the existing label.
4. If the provider confirms no label was created, assess whether replay is safe.
5. Reuse the original idempotency key.

### D. Malformed provider response

1. Record the response error.
2. Query the provider using the original idempotency key.
3. Verify whether the label was created.
4. Reconcile any existing label.
5. Replay only after verifying the provider record and idempotency behavior.

### E. Duplicate delivery or replay

1. Identify the original idempotency key.
2. Look up the existing label.
3. Reuse the original label ID.
4. Do not purchase a second label for the same request.

The fake gateway demonstrates this by returning the existing label for a repeated key.

## 7. Retry policy

The retry engine supports:

- Maximum attempts from 1 to 10.
- Exponential backoff.
- Configurable backoff multiplier.
- Maximum backoff limit.
- Retry classification for transient errors.
- No automatic retry for permanent or unknown errors.

## 8. Known limitations

- The shipping provider is simulated.
- The idempotency gateway stores records in memory.
- Records are lost when the process restarts.
- The timeout helper cannot terminate an already-running Python worker thread.
- Provider status lookup is demonstrated through a fake adapter.
- Metrics contain local latency measurements, not production SLAs.
- Current metrics record final workflow states, not time spent in each state.
- Persistent storage, distributed locking, and real provider reconciliation are outside this prototype.

## 9. Operational safety rules

1. Never log API keys, passwords, tokens, or credentials.
2. Never replay a timed-out purchase without checking provider status.
3. Reuse the original idempotency key during recovery.
4. Stop automatic processing after permanent failure or retry exhaustion.
5. Preserve trace and evidence files for investigation.
6. Require operator review before uncertain recovery actions.
